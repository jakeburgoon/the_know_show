# The Know Show v1.15.0 — working candidate (not cleared for deployment)

This branch starts from the saved v1.14.0 private-review source. It does not modify the live repository, database, or game deployment. The original question banks are unchanged in this candidate. Use the testing branch only; do not replace your production files yet: a real Next.js build, Supabase migration/RPC test and browser playtest are still required.

## What is implemented in the candidate

- First-pass inventory: 79 categories, 1,047 regular questions, 82 category-linked Final Word entries (74 eligible), plus 18 legacy Final Word records retained in code for compatibility. 10 approved overlapping super categories; 15 seasonal categories, five wholly visual regular categories, and 75 regular image items. See `V115_CATEGORY_AUDIT.csv`, `V115_QUESTION_INVENTORY.csv` and `src/lib/category-taxonomy.json`. This is a classification/inventory audit, not a fresh fact-check or licensing clearance.
- Question Lab and Category availability super-category filters. Each question inherits category tags and can have extra tags. No host curation, entitlements or access gates added. Existing categories retain all IDs, scheduling, availability and question weighting rules.
- Question editor for regular and Final Word entries, reachable from the existing flagged-question link to Question Lab. Add a question, edit wording and answers, aliases, difficulty, category, choices/hints, source reference, extra tags, publication status; preview and test answers; save draft, publish, load previous content as a new revision; optionally resolve associated flags. New IDs are assigned by the server. Image edits can reference existing bundled image files; image uploads and new-category creation are deferred. Drafts must be structurally valid to save. Review factual accuracy and usage rights before publishing.
- Append-only published revisions, drafts, and immutable library snapshots in a service-only Supabase migration. New shows pin the effective library separately from the room snapshot. Ongoing games use that pinned library, including scoring and feedback. Existing active v1.14 rooms without a catalog reference use the base files; finish them before deployment. A rematch reloads current revisions at the next show start. The four-enabled-questions-per-difficulty draft rule is unchanged: disabling or moving one of four may make that category temporarily unavailable for regular rounds. The dashboard displays per-level counts; at least 12 year-round playable categories and nine eligible year-round Final Word categories must remain. Published changes affect future shows. Historical IDs remain stable; new exposures capture revision/prompt/answer in diagnostic metadata, while aggregate statistics still combine revisions under the same ID.
- Library synchronization: `Export published revisions · JSON` in Question Lab produces a full ordered export. `npm run library:sync -- /path/to/know-show-library-revisions.json` merges it into both permanent bank JSON files and `src/lib/library-sync.json` (watermark). Alternatively, with local environment credentials, `npm run library:sync -- --live`. Commit these three files together after review and before each software release. The prebuild check compares the live published watermark against the repository ledger and rejects a production build with unsynchronized revisions. An edit published after the check remains a live overlay and must be merged at the next release; if it lands before the check, re-export. Disabled questions remain as records/tombstones; drafts never enter the export. Do not delete the Supabase revision log or catalog snapshots after sync. Do not commit credentials or exported raw revision files.

## Required verification before production

1. Install actual dependencies on a network-connected machine; run `npm install`, `npm run typecheck`, `npm run test:types:game`, `npm run test:engine`, `npm run test:ui`. Then run `npm run build` with a staging Supabase project's environment. The original app requires Node 20+.
2. Back up the database. On staging, run `supabase/upgrade_v1_15_0.sql` after the previous migrations. Confirm service-only access, exports, draft writes, conflict checks, and the publish transaction. Verify no anon/authenticated users can read the new tables or run the RPCs. This migration is additive but has not been executed in this environment.
3. Sign into the developer dashboard, browse a flagged question, save draft and verify not live; publish an edit and optionally resolve flag; create regular and Final Word questions; disable and restore a question. Check validation and draft coverage. Play two games across a publish, verifying first retains old content and second gets new content. Test a rematch. Check shared screen, phone, scoring, exposure journal, written/choices behavior, and image failure handling. Verify no answers leak before reveal.
4. Export revisions, merge on a clean staging source tree, repeat merge (must be no-op), build and deploy staging, confirm same questions are live. Confirm build gate refuses an unsynchronized revision. Check rollback/restoration without losing IDs. Only then prepare the production upgrade package and deploy. Do not run migration or code on production until ready.

## Design decisions / limits

No audio or TV layout redesign. No fresh question wording or factual changes in the shipped baseline. The ten taxonomy names are approved; individual memberships are a first-pass classification (not exclusive). Category creation, direct asset upload, full content licensing audit, per-revision aggregate statistics and future host curation remain later work. This candidate includes implementation, but real framework compilation and live database/browser tests are not complete.
